# CPRMV: building the specification in a pinned container

Status: draft, 27 November 2026; review by Bas pending

Closes #24 and the remaining items of #21. Companion to the daily `npm audit` of
`html/package-lock.json` (branch `chore/npm-audit`), which merges with or after
this change.

## Intent

The ReSpec specification (`html/`) is built by `npm run build` on one maintainer's
Mac and committed as built output: `html/public/<version>/` (published by GitLab
Pages), `serve_api/respec/` (served by the API) and the PlantUML diagrams in
`html/media/`. The build only runs on macOS (`sed -i ''`, #24), needs five
toolchains installed by hand, and its npm tree carries 24 Dependabot alerts (#21).

The build moves into a container that anyone with Docker can run, and CI checks
that what is committed is what the sources produce.

## What a Linux build produces today

Measured on 27 November 2026, in `node:26-bookworm` with Debian's Chromium 156,
OpenJDK 17, rdflib 7.6.0 and the PlantUML jar named in `html/package.json`, from
`acc` at `7663cd7`:

| Output | Compared with what is committed |
| --- | --- |
| `public/0.4.3/index.html` (ReSpec render) | **Byte-identical**, with respec 35.2.2 and with 37.5.1 |
| Markdown generated by `shaclgen.py` (`ch03.md`, `methods.md`, `modules.md`) | Identical |
| `puml/*.puml` (98 files) | 95 identical. `class.Rule`, `class.RuleSet` and `overview` show `hasPart` as an attribute instead of an arrow `--> "0..*" Rule`. Deterministic across `PYTHONHASHSEED` values, so it is a difference in Python or rdflib between the Mac and the container, not randomness |
| `media/*.png` (PlantUML) | All differ in bytes (fonts, Graphviz); not compared by eye yet |
| `cprmv.pdf` (pandoc) | Fails with Debian's pandoc 2.17: pdflatex cannot embed the Logius SVG logo. Builds with pandoc 3.8 (`rsvg-convert`), but two runs differ in 168 bytes, also with `SOURCE_DATE_EPOCH` and `FORCE_SOURCE_DATE` |

So the HTML, which is what readers use, reproduces exactly. The respec 35 to 37
upgrade does not change the output. The diagrams and the PDF need one regeneration
in the container, which becomes the new baseline.

## Design

### `html/build.sh`

The `build` entry of `html/package.json` becomes `sh build.sh`; the chain moves into
a POSIX script, shellchecked in CI like the other scripts:

1. version from `package.json` (`npm pkg get version`), validated as `^[0-9]+\.[0-9]+\.[0-9]+$`;
2. `python3 shaclgen.py` (Markdown and `puml/`);
3. `npx respec --no-sandbox --localhost --src index.html --out public/<version>/index.html`;
4. strip the `file://` prefixes with `sed -E … > tmp && mv` (the #24 fix);
5. PlantUML to `media/`; copy `template/` and `media/` into `public/<version>/`;
6. pandoc to `public/<version>/cprmv.pdf`;
7. copy `public/<version>/` to `serve_api/respec/<version>/` and `serve_api/respec/`, as today.

It fails on the first error (`set -eu`) and assumes it runs in the build image; it
installs and downloads nothing itself. The PlantUML jar is part of the image, so
the `get-plantuml` script and the `config.plantuml_jar` entry go.

### `html/build.Dockerfile`

One image with every tool, pinned the way the API image is:

- base `node:26-bookworm@sha256:…` (Renovate `docker:pinDigests`);
- Debian `chromium`, `default-jre-headless`, `graphviz`, `librsvg2-bin`, and a
  minimal TeX Live (`texlive-latex-base`, `-latex-recommended`,
  `-fonts-recommended`, `lmodern`) from the pinned base's apt sources. These are
  not version-pinned, as for the runner image's tools: the digest pins the base,
  not the packages installed on top;
- pandoc 3.8.3 from its GitHub release `.deb`, verified against a SHA-256 in the
  Dockerfile (Debian bookworm ships 2.17, which cannot build the PDF);
- the PlantUML jar (the version in `package.json` today) at a SHA-256;
- Python: `html/requirements.in` (`rdflib`), compiled with hashes to
  `html/requirements.txt` by the same pip-tools setup as `serve_api/`, installed
  with `--require-hashes` into a virtualenv. Renovate's `pip-compile` pattern and
  the daily audit gain that file;
- `npm ci` with `PUPPETEER_SKIP_DOWNLOAD=1` and
  `PUPPETEER_EXECUTABLE_PATH=/usr/bin/chromium`, so puppeteer does not download a
  browser at install time.

A pinned `pandoc/latex:3.8` base was considered: it is Alpine with TeX Live and
pandoc 3, but adding Node 26, Chromium, Java and Python to it gives a less usual
stack than the reverse.

### Running it

`scripts/build-spec.sh` (repository root) builds the image and runs `html/build.sh`
in it with the checkout mounted, as the invoking user so the output is not owned by
root. On any machine with Docker, including Windows with Git Bash and the Mac:

```
sh scripts/build-spec.sh
```

The README's "Building the specification" section replaces the toolchain list in
`html/README.md`.

### The check in CI

`.github/workflows/spec.yml` ("Specification"), on pull requests and pushes that
touch `html/**`, `rdf/**`, the build files or the workflow:

1. build the image (no push, `cache-from` the GitHub Actions cache), run
   `scripts/build-spec.sh`;
2. `git diff --exit-code` over everything except `*.pdf`: the HTML, the Markdown,
   the PlantUML sources and the PNGs must match what is committed. The PNGs are
   compared because the baseline now comes from this image; if they prove not to
   reproduce between two runs of the same image, they move to the "builds" class
   below and the spec records it;
3. the PDF must build and be non-empty; it is not compared, because pandoc's PDF
   is not byte-reproducible;
4. upload `public/<version>/` as a 30-day artifact, so a reviewer can look at the
   result without building.

Pins as elsewhere (checkout, the Docker actions, `persist-credentials: false`,
read-only token). It is not a required check at first: it needs the network
(Logius' ReSpec profile, fetched during the render) and is slower than the
others. Once it has run green for a release, it can join the rulesets.

Because the render loads Logius' unversioned profile, a change there makes the
HTML differ on the next run, in whatever pull request touches `html/`. That is
intended: the committed specification no longer matches what a build produces,
and the fix is to rebuild and commit. The failure message says so.

### The toolchain upgrade

- `respec` `^37.5.1` (the newest release at least 14 days old) and
  `"engines": { "node": ">=26" }`; `html/package-lock.json` resolved with
  `npm install --package-lock-only --ignore-scripts --before=<14 days ago>`. `npm
  audit` then reports 0 advisories, against 24 Dependabot alerts now; `extract-zip`,
  `basic-ftp`, `tar-fs`, `ip-address` and `js-yaml` leave the tree.
- The upgrade is a major (35 to 37), which Renovate holds for Dependency Dashboard
  approval; it is made here by hand, with the render comparison above as the
  assessment.

### The first baseline

The pull request regenerates every output once in the container and commits it:
all PNGs and the PDF.

**`hasPart` stays as in the current diagrams** (decided 27 November 2026): the
arrow `RuleSet --> "0..*" Rule : hasPart` (and `Rule --> "0..*" Rule`), not an
attribute. The difference comes from `shaclgen.py` under the container's Python and
rdflib 7.6.0, so the cause is found and fixed in `shaclgen.py`, in this pull
request, before the baseline is taken; the three `puml` files then stay as
committed. A test for `shaclgen.py` pins it: the generated `class.Rule.puml` holds
the arrow.

Bas checks the regenerated PNGs and PDF by eye when he is available; the artifact
from the workflow is there for that.

### Docs

- README: "Building the specification" (the one command; what it writes where).
- `SECURITY-PIPELINE.md`: the pin register (the build image's base digest,
  pandoc 3.8.3 and PlantUML with their checksums, Node 26 for the ReSpec build),
  the checks table (`spec`), and the remaining #21 item: `audit`'s
  `npm ci --dry-run` and registry signatures for `html/` are not adopted, because
  the build image runs `npm ci` from the lockfile in CI on every change, and the
  daily `npm audit` covers advisories.

## Not in this change

- GitLab Pages building the spec itself. It keeps publishing the committed
  `html/public/`, which this check now holds to the sources.
- Vendoring the Logius ReSpec profile (the accepted `missing-integrity` finding on
  `html/index.html:14`). The build still fetches it during the render.
- Byte-reproducible PDFs.
- Changing what the build produces, beyond the `hasPart` decision.
